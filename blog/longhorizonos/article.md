# LongHorizonOS 面向自我改进 Agent 的运行时

长程 Agent 不只需要记住历史，还要决定：**先做哪一步、并行多少、带入哪些信息，以及变更后从哪里恢复。**

LongHorizonOS 把任务、上下文与资源放进可检查的运行状态中，让调度决策能够追溯其依据。

## 从依赖与版本确定当前状态

“测试通过”应关联来源版本、配置和验证器。来源改变后，相关结论需要重验；其他历史仍保留，适用性另查。

图 1｜状态示意：失效沿已声明依赖传播；未知关系仍是未知，图本身不证明语义正确。

## 调度优化放在什么位置

图分析产生就绪前沿与可选优先级信号；策略提出执行批次，Scheduler 再核对当前版本、所有权和实际容量。上下文组件为执行准备工作信息。

![LongHorizonOS调度架构](assets/figure-2.jpg)

图 2｜实现模块图：不同入口按 profile 接入；右侧虚线组件不代表默认全部串联。

已有优化包括增量图分析、联合选批、争用退避、流式补位，以及记忆闭包、需求覆盖规划和受预算约束的驻留恢复。不同排序策略保持区分。

## 联合选批为什么有用

分别挑选“无冲突任务”和“放得下的任务”，再取交集，可能漏掉可行批次。联合检查只为真正选中的任务扣减容量和预算。

## 为 AI4AI 提供运行基础

[ResearchBoost](https://ydove0324.github.io/hx_resume/blog/researchboost/) 用可靠反馈推进训练代码优化，[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) 探索 Agent 的代码自修改。LongHorizonOS 希望承担其中的运行责任：管理版本、执行、上下文和预算，由独立评估器判断改进。

![AI4AI目标分工](assets/figure-4.jpg)

图 4｜应用目标：候选生成、运行管理与效果评估各有职责。

## 当前边界与验证目标

这些机制已有代码基础，但接入范围不同：SDK 调度、原生 harness 记忆策略和动态需求原型不能混作同一条已验收路径。动态合同仍有条件观察范围的已知限制。

下一步要在相同信息与预算下，比较普通版本管理、checkpoint 和检索，核算完整 reward、墙钟时间、输入、缓存读取、输出及失败开销。整体收益仍待实验验证。

[ClawVM](https://arxiv.org/abs/2604.10352) 的驻留管理、[PlanFence](https://arxiv.org/abs/2609.03340) 的版本准入是直接相关基础；系统增益需要在强基线上验证。
