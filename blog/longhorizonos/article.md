# LongHorizonOS 面向自我改进 Agent 的运行时

一个 Agent 在代码版本 A 上完成测试，记下“正确性通过，热点位于模块 M”。随后，它修改了共享函数，得到版本 B。经过一次上下文切换，Agent 根据先前结论继续优化。

这时，“测试通过”仍能作为执行依据吗？它对应哪个版本，修改影响了哪些路径，哪些结果可以复用，哪些需要重新检查？这些问题决定了下一轮工作是在积累进展，还是在失效的前提上继续消耗预算。

LongHorizonOS 希望研究这样的运行时问题：**让长期 Agent 获得当前行动需要的有效状态，并在有限资源下完成准备、执行、验证和恢复。** 自我改进 Agent 是这一方向的重要应用。

## 一条实验结论需要携带适用条件

长期任务会产生大量日志、文件和测试结果。保存原始记录有助于追溯，但执行下一步时，系统还需要知道这些结果的适用条件。

例如，“测试通过”应当对应具体的代码版本、配置与验证器；“优化没有收益”应当对应当时的工作负载和测量条件。否则，同一句结论可能被用于不同的程序和预算，甚至掩盖了两次实验并没有进行公平比较。

代码更新也不意味着全部历史都应该丢弃。修改一个文件，可能只影响少数结果；重新读取和验证全部历史，又会增加成本。我们关注的是：怎样表达结果与来源的关系，让局部变化引起范围明确的检查，并让下一轮行动知道自己依赖了什么。

文本摘要和检索可以帮助找到信息。结果是否依然适用于当前行动，还需要版本、依赖和实际执行记录共同支撑。

## 自我改进使试验状态成为持续资源

AI4AI 用 AI 改进 AI 的算法、软件或研究过程。[AlphaEvolve](https://arxiv.org/abs/2506.13131) 通过程序修改与自动评估推进搜索；[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) 修改 Agent 自身的代码，并维护经过下游任务评估的变体档案。

[ResearchBoost](https://ydove0324.github.io/hx_resume/blog/researchboost/) 把目标落在训练代码优化上：固定工作负载与正确性要求，从 profile 出发修改瓶颈，再由独立裁判和完整运行检查结果。这些工作让反馈成为下一轮改进的输入。

当改进持续多轮，Agent 需要保留候选的来源、修改内容、失败原因与成本。一个实验结果可能在数小时后被复用，而期间的代码、环境和目标已经变化。运行时需要维护这段过程，使后续行动能够找到可用证据，并区分事实、模型假设和仍待验证的判断。

LongHorizonOS 与 AI4AI 的连接就在这里：模型提出候选，任务评估器检验效果，运行时维护两者之间持续变化的状态和资源。这为自我改进提供执行基础，也保留了评价过程的独立性。

优化策略可以变化，评价条件需要独立管理。若测试标准、任务或环境改变，应当记录相应版本并重新判断结果能否比较，避免候选通过改变评价条件获得表面上的“进步”。

## 用图表达当前行动的依据

图适合表达有明确来源的结果。在目标设计中，测试节点关联源文件版本、配置和验证器；行动节点声明需要哪些材料或结果。来源更新后，系统沿已知依赖标记受影响的节点，再决定是否重新准备。

对于开头的例子，版本 A 的测试记录仍然保留。若动作依赖的共享函数已改变，系统应重新检查相关依据；若一个结果与此次修改没有已知依赖，则可以进一步判断其复用条件。历史保留和当前可用性由此成为两个不同的属性。

这一过程要求区分证据等级。Agent 说“我已经验证”，工具实际完成验证，以及验证结果确实对应当前来源，是三种不同的记录。送入模型的内容还需要单独记录，才能确认恢复材料已经交付。

图只能处理被正确表达出来的关系。模型未声明的语义依赖，不会因使用了图就自动出现。因此，运行时需要保留未知状态，并为重新查证或补充依赖提供路径。

## 把恢复操作与预算一起考虑

缺少执行依据时，系统可以读取当前来源、重新运行测试，或恢复满足条件的历史结果。这些操作具有不同的时间、token 和工具成本。恢复之后，也必须留出完成有用工作的预算。

我们希望让调度围绕当前行动展开：先检查已声明前提，再选择受支持的准备或恢复操作；执行完成后，将结果及成本提交回状态。工具调用尚未确认结束时，系统不能提前把它记作已完成进展。

资源核算还需要覆盖失败路径。恢复没有产生可用状态，已经发生的输入、输出和工具工作也不能从账本中消失。并行执行时，总耗时应按实际关键路径衡量，不能把重叠阶段简单相加。调度追求的应是完整任务的净进展。

压缩与 memory 也可以放到这一过程中判断。原始日志保留追溯材料，结构化状态描述来源和依赖，当前上下文承载接下来需要使用的信息。某段信息可以暂时离开上下文，但其身份、适用条件和恢复入口应当能够保留。

调度策略需要权衡驻留与恢复：持续携带所有历史会增加输入，频繁压缩和重读也有代价。目标是根据当前需要选择合适的表示和准备动作，并将额外维护开销一起计入，而不预设一种策略适合所有任务。

## OS 责任体现在哪里

这里的 OS 指向运行时责任：管理有限资源、跟踪状态生命周期、检查执行前提、处理失败，以及确定动作何时可以提交。

传统系统中的版本控制、增量构建、缓存一致性和资源所有权，为这些责任提供了基础。Agent 的特殊困难在于，部分需求和依赖来自模型判断。运行时可以精确检查明确的版本、预算和执行记录；对自然语言结论的正确性，仍需要任务相关的验证。

[MemGPT](https://arxiv.org/abs/2310.08560) 已将分层内存思想引入上下文管理。[ClawVM](https://arxiv.org/abs/2604.10352) 研究 harness 中状态的驻留、持久化和写回合同，[PlanFence](https://arxiv.org/abs/2609.03340) 检查计划所依据的输入版本是否仍然有效。LongHorizonOS 应在这些直接相关的基础上，检验恢复操作、依赖有效性和资源约束相互作用时，还存在哪些值得解决的问题。

这些能力既可以通过 harness 内部接口实现，也可以接入其事件和闭合调用边界。接入位置决定可观测与可控制的范围，系统收益则需要通过具体任务衡量。

## 当前基础与验证目标

LongHorizonOS 当前研究代码包含显式依赖与版本状态、部分恢复与 harness 接入，以及资源核算机制，并有固定输入的离线检查。动态语义需求、自动来源记录和跨路径覆盖仍需完善；统一闭环和真实任务收益尚未完成验证。

接下来的研究假设是：一次局部来源变化，是否会引起本可避免的大量失效、重验和恢复？需要先记录真实触发和信息交付，再与获得相同观测的版本管理、checkpoint 和检索方案比较。若提出新调度算法，还应解释它利用的结构，以及扣除维护开销后剩余的收益。

对长程任务，我们关注固定时间或费用下的 reward，并分别核算未缓存输入、缓存读取、输出 token、壁钟时间和失败成本。对自动优化任务，还可以观察固定总预算内，独立评估器确认的最佳候选质量如何变化。增加尝试次数本身，不等于获得了更多有效改进。

LongHorizonOS 面向自我改进 Agent 的目标，是让每轮行动拥有可检查的依据，让有效结果在适用范围内被复用，并使有限资源持续投入经验证的进展。
