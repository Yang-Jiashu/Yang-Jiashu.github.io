# LongHorizonOS：把状态准备与任务执行一起调度

长程 Agent 持续改变代码、环境和计划，上下文却只能容纳有限信息。每一步既要决定**做什么**，也要决定**凭什么继续做**。

LongHorizonOS 探索一个统一问题：**在有限上下文、时间和调用预算内，协同管理有效任务状态与执行，让预算转化为更多经验证的任务进展。**

## 上下文与执行，为什么需要一起调度

材料已经驻留、依据仍然有效时，一步任务可以直接推进；材料缺失或依据过期时，需要先加载、恢复或重验。执行次序与写入又会改变下一轮的工作集。

![状态与执行的双向关系](assets/figure-1.jpg)

图 1｜问题结构：状态影响执行成本，执行改变后续状态。

## 一个闭环，管理准备与执行

每轮形成同一份计划：推进哪个步骤、复用什么状态、补齐哪些材料、占用多少资源。执行结果再更新状态与下一轮调度。

![状态准备与执行的统一闭环](assets/figure-2.jpg)

图 2｜统一设计目标。现有模块接入范围不同，尚未在所有 harness 中统一验收。

Graph 记录显式依赖与适用条件，memory 保存持久状态，context 承载当前工作集。运行时负责准入、资源分配和结果提交；已声明依赖之外的关系仍需观察与验证。

## 调度优化，落到每一次决策

已有实现包括**增量图分析与倒排索引、记忆闭包与覆盖规划、联合选批与流式补位**。它们分别减少重复计算、准备必要材料、安排可行执行；具体入口与开关见实现对照。

![容量与冲突联合选批示例](assets/figure-3.jpg)

## AI4AI：让长期改进有运行基础

[ResearchBoost](https://ydove0324.github.io/hx_resume/blog/researchboost/) 通过可信反馈推进训练代码优化。LongHorizonOS 关注持续迭代的运行成本：跨轮次管理状态、上下文和资源，让独立评估器判断改进是否成立。

## 怎样判断系统真的有效

在相同模型、任务、信息权限和预算下，对比具备版本管理、checkpoint 与检索的强基线，检验联合管理是否带来净收益。

最终看任务质量、完成时间与完整 token 成本；准备、恢复、重验和失败开销全部计入。现有局部优化已有代码依据，整体 reward 与成本收益仍需真实任务验证。
